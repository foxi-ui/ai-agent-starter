ai-chat · SSE 是怎么解析的

一条事件，可能被切成两半

src/llm/sse.ts 只有 82 行，却是整个项目里最容易写错的一块。 难点不在语法，在一个反直觉的前提上：网络交给你的不是「消息」，是字节。

服务端按「事件」写，你的程序按「块」收，两者的边界毫无关系。

所以分帧的本质是：自己攒、自己找边界、把不完整的留给下一次。 这页把它拆成 4 层来看 —— 每一层只解决一个问题。

第一步

TCP 不给你「消息」这个概念

服务端把 4 条事件写进连接，它们在服务端那边是清清楚楚的 4 段。 但这 4 段怎么送到你的程序里，TCP 完全不保证： 它只保证字节顺序不变，不保证「一次 read() 恰好给你一条消息」。

这正是 parseSse 存在的理由。它不假设块和事件有任何对齐关系 —— 每次只做一件事：把手上的文字尽量切成完整事件，切不动的原样留下。

第二步

SSE 的格式其实只有 4 条规则

事件是纯文本（不是 JSON、不是二进制），格式是文本行： 每行 字段名: 值，一段事件结束时打一个空行。

这 4 条正好对应 parseBlock 里的 4 个判断。 其中第 ④ 条最容易忽略 —— 它是「只有注释的块」和「只有 event: 的块」都不会 产出事件的原因，测试里专门有两条钉着它。

第三步 · 关键

「解码」和「分帧」是两层，不能混

这是最容易搞混的一点。网络给你的是字节（Uint8Array）， 而 parseSse 收的是字符串。中间那一步是解码， 它不属于 sse.ts —— 它写在 deepseek.ts 里。

为什么这层不能省：中文会被切在中间

一个中文字在 UTF-8 里占 3 个字节。切割线落在第 1 个字节之后时， 两次 read() 各自拿到的都不是完整字符。 下面是真的跑出来的结果：

第四步 · 核心

parseSse 的形状：残余接力

它的签名看起来有点怪 —— 为什么要传一个 buffer 进去、又要一个 rest 出来？ 因为它自己什么都不记。「攒着没切完的那半截」这件事， 被交回给调用方保管，下一次再传进来。 

parseSse(chunk, buffer?) → { events, rest }
         ↑新到的     ↑上次剩下的        ↑这次能切出的  ↑留给下次的

这个形状有个直接好处：它是纯函数 —— 没有 this、不碰网络、不写输出。 于是 12 个测试全部是「喂一个字符串、断言一个对象」，不需要造假的可读流。 这是设计上的取舍，不是偶然：注释里写得很清楚，这么做的目的就是让最容易出错的逻辑可测。

第六步

三个最容易写错的地方

这三处都有专门的测试钉着。它们也是这份代码存在的全部难点 —— 除此之外都是平铺直叙。

坑 ①　先规范化还是先拼接？

直觉写法是先把手上的残余清理干净、再拼新数据。那是错的。 因为残余的尾巴上可能挂着一个落单的 \r —— 它到底是「一个独立的 \r」，还是「和下一块开头的 \n 配成一对」， 单看残余是判断不了的。

✗ 先规范化 buffer，再拼接

残余 "data: a\r" 里的 \r 被单独规范化， 下一块开头的 \n 就再也配不上它。
实测结果：事件条数不变，但 \r 漏进了内容 —— data 拿到的是 "a\r" 而不是 "a"。

✓ 先拼接，再整体规范化

拼成 "data: a\r\n\r\n" 之后，\r\n 成对出现， 一次 replace(/\r\n/g, '\n') 就对了。落单的 \r 也留在 rest 里等下一次。

实测：CRLF 被切在两次 read 之间 对应 sse.test.ts 第 30 行那条用例
parseSse("data: a\r") → events=[]　rest="data: a\r"
把 rest 原样传回去，再喂下一块
parseSse("\n\r\n", "data: a\r") → events=[{ data: "a" }]　rest=""
尾部的 \r 必须留在 rest 里 因为在这个实现里，落单的 \r 就是普通字符（只有 \r\n 才是换行）。 若提前把它剥掉，它会从事件内容里静默消失：源字节 data: a\rb\n\n 切在 \r 与 b 之间时，data 会变成 "ab" 而不是 "a\rb"

坑 ②　空行才是边界，单个换行不是

data: 可以出现多行，它们属于同一条事件。所以判断边界必须是 \n\n（空行），不能是 \n。

实测对比
parseSse("data: 一\ndata: 二\n\n") → 1 条事件，data = "一\n二"
parseSse("data: a\n") → 0 条事件，rest = "data: a\n" 只有一个换行 = 还没结束

坑 ③　切不动的时候，要原样留存而不是报错

「半条事件」是常态而非异常。如果代码在切不出事件时报错或丢弃， 只要网络把事件切开一次，那半条数据就永久丢了。 正确的做法是把它放回 rest，等下一位。

第七步

它故意「不懂」DeepSeek

sse.ts 里没有一个 DeepSeek 或 OpenAI 的字段名 —— 没有 choices、没有 delta、没有 reasoning_content。 连 [DONE] 它都不认识。

12 条测试全部是「喂字符串、断言对象」的形式，所以你可以直接改一行代码看哪条变红 —— 这是理解这份代码最快的路径。

想验证什么怎么改坏它哪条会红（实测）

最后

几个容易卡住的点

为什么要缓冲区，不能读到就解析吗？

因为一次 read() 的边界和事件边界无关。 读到就解析的话，只要事件被切开一次就会解析失败。 缓冲区保存的正是「已经到达、但还构不成一条完整事件」的那部分。

为什么是纯函数，不做成有状态的类？

纯函数可以用「喂字符串、断言字符串」测穿，不必构造假的可读流。 换来的代价是调用方要负责保管 rest —— 但这个项目里只有一处调用点。

中文乱码是分帧的 bug 吗？

不是。sse.ts 只处理字符串，它看不到字节。 乱码发生在它上游 —— TextDecoder 必须带 { stream: true }， 否则被切开的多字节字符会变成不可逆的替换字符。

rest 会不会无限增长？

正常不会 —— 每次 read() 都会尝试切块，切出来的立刻变成事件。 但如果上游一直发数据却永远不发空行，它确实会一直涨。 这属于「错误处理」，记在待办里，不在这一版解决。

为什么不用现成的 SSE 库？

这是学习项目，本项目的硬约束是零运行时依赖， 目的是亲手走通协议这一层。而且这段代码只有 82 行、12 条测试， 维护成本比引入依赖更低。

为什么要单独一个文件，不写在 deepseek.ts 里？

为了保住「纯函数可测」这个性质。deepseek.ts 里全都是 fetch、reader、超时计时器这些 IO； 混进分帧逻辑后，测分帧就不得不碰网络。
