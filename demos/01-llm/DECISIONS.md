## D1. 零运行时依赖，手写 `fetch` 而不是用 SDK

**决策**：`dependencies` 为空，直接用原生 `fetch` 调 `/chat/completions`。

**理由**

- 这是学习项目，目标是弄清「LLM API → 消息结构 → 上下文管理」这条链路本身。
  用 SDK 会把请求构造和响应解析藏起来，正好遮住要学的东西。
- OpenAI-compatible 的 `POST /chat/completions` 契约很小，手写成本低于引入依赖的成本。
- 零依赖没有传递依赖、没有升级负担、没有安全面。

**代价**：后续要自己处理流式解析、重试、退避等 SDK 本来提供的能力。
这个代价是**有意接受**的，因为那些正是后续增量的学习目标。

## D2. 三层内核，而不是单文件

**决策**：`cli → core → llm` 单向依赖，而不是把逻辑写在一个 `index.ts` 里。

**理由**

单文件版本能跑，但**无法在无网络下测试**——网络调用和 `console.log` 混在一起，
任何断言都得真的发一次请求。

分层后，关键收益是 `LLMClient` 这个接缝：CLI 只依赖接口，测试传入手写替身，
于是「一问一答」「报错后继续」「多轮上下文形状」全部变成离线断言。

**代价**：多几个文件、多一层间接。对 7 个源文件的项目来说，
换来的是**全部 CLI 行为可测**，值得。

---

## D3. 非流式先行

**决策**：本次一次 `fetch` 拿完整回答，不做 SSE。

**理由**：流式的复杂度在协议层（SSE 分帧、事件归一化、增量拼接），
和「上下文管理」是两个正交的难点。同时引入会让两边都学不透。

**代价**：等待期间没有输出反馈。**明确推迟，不是遗漏。**

---

## D5. 不做自动重试

**决策**：任何失败只打印一次错误，然后继续循环。

**理由**：在错误分类（限流 / 超时 / 鉴权 / 服务端错误）尚未建立之前，
盲目的自动重试会让**限流雪上加霜**，也会让用户分不清「慢」和「挂了」。
先做到「不崩溃、不污染上下文」，把重试留到 M6 与错误分类一起做。

**代价**：偶发网络抖动需要用户手动重发。

## D6. thinking 默认开启，但只打印 `content`

**决策**：不传 `thinking` 参数（跟随 API 默认），响应中忽略 `reasoning_content`。

**理由**：默认行为最省心，不额外发送本次用不到的参数。而 `reasoning_content`
属于模型的中间过程，打印出来会淹没最终答案，也**不应进入上下文**——
把它带进下一轮请求会浪费 token 并可能干扰后续推理。

**代价**：调试时看不到思考过程。后续用 `--show-reasoning` 显式开启。

**已由 D22 部分修订**：不再被完全忽略 —— M2a 起它被归一化成 `reasoning-delta`，
由渲染器折算成 stderr 的一行 `[思考中…]` 指示（仍不打印全文、仍不进上下文）。

## D7. 失败的轮次不写入 assistant 消息

**决策**：`session.append('assistant', ...)` 只在 `chat()` 成功返回后执行。

**理由**：如果在失败时追加一条空 `assistant` 消息，历史中就出现一条**伪造的回答**。
模型会在下一轮把它当作自己说过的话，产生自我矛盾的推理。

**代价**：历史中会保留失败的 `user` 消息。这是正确的——
用户确实说过那句话，缺失的只是系统没能给出的回答。

---

## D8. `Session` 不做 system prompt 的存储

**决策**：`Session` 只存 `user` / `assistant`，`system` 由 `toMessages(systemPrompt)`
在组装时注入。

**理由**：`system` 是**每次请求都必须重新放在首位**的稳定前缀，而不是对话历史的一部分。
把它隔离在外之后：切换系统提示不需要重建会话；测试也能传空串来省略它。

**代价**：调用方必须记得传 `systemPrompt`。但只有一个调用点（`repl.ts`）。

---

## D9. 用异步迭代器而不是 `rl.on('line')`

**决策**：用 readline 的异步迭代器串行处理每一行。

**理由**：事件回调里无法自然地 `await`。若在回调中并发发起请求，
快速输入会让多个请求同时在途，**响应顺序与输入顺序不一致**，上下文随即错乱。

**代价**：无法在等待响应时并发处理新输入——但这正是我们想要的语义。

> 具体写法后来从 `for await` 改成手写迭代器，见 D15。

---

## D10. 采用 `@/` 路径别名，并为此注册运行时钩子

**决策**：源码统一用 `@/` 指向 `src/`，并在 Node 运行时注册 `resolve` 钩子
（`loader.mjs` + `loader-hooks.mjs`），而非只用相对路径。

**理由**：别名让跨层导入意图更清晰（`@/core/session.ts` 比 `../../core/session.ts` 好读），
在层级加深后收益更明显。

**关键代价 —— 必须知道的坑**：Node 的原生类型擦除**不读取 `tsconfig.json` 的 `paths`**。
`tsc` 认这个别名，Node 不认。因此：

- 别名出现在 `import type` 里能「侥幸」工作，因为整条语句在运行前被擦除；
- 别名出现在**值导入**里会直接抛 `ERR_MODULE_NOT_FOUND`。

**解决**：用 `module.register()` 注册钩子，零依赖（只用 `node:` 内置模块）地把
`@/x` 映射回 `src/x`。必须拆成两个文件——**`--import` 只是导入模块，
不会自动把 `resolve` 导出当作钩子**。

**替代方案与为何不选**：

| 方案 | 为何不选 |
| --- | --- |
| 全用相对路径 | 放弃别名可读性；本次已明确选择保留别名 |
| 用打包器 / `tsc-alias` 重写路径 | 引入依赖或构建步骤，破坏「零运行时依赖 + 直接跑 `.ts`」 |
| `package.json` 的 `imports` 字段 | 原生零依赖，但只支持 `#` 前缀，无法保留 `@/` 写法 |

**代价**：多两个文件，多一个需要理解的机制，且 `start` / `test` 脚本必须带 `--import`。
若两者不一致，测试通过但 `pnpm start` 会挂——**改动脚本时需同时改两处**。

## D11. 开启 `allowImportingTsExtensions`

**决策**：`tsconfig.json` 设 `allowImportingTsExtensions: true`。

**理由**：本项目在值导入中写显式 `.ts` 扩展名（`'./x.ts'`），这是配合
Node 原生类型擦除的要求（运行时需要真实文件名）。而不开这个选项，
TypeScript 对**值导入**的 `.ts` 扩展名会直接报 `TS5097`。

该选项要求 `noEmit`（或 `emitDeclarationOnly`），本项目已是 `noEmit: true`，无冲突。

**代价**：几乎没有——项目本就不产出 JS，由 Node 直接运行 `.ts`。

---

## D12. 用 `--env-file-if-exists` 加载 env 文件

**决策**：`start` / `test` 脚本前置两个 `--env-file-if-exists`，依次加载 `.env`（模板，入库）
与 `.env.local`（真实值，已 gitignore）。

**理由**

- Node **不会自动加载 `.env`**。没有这个标志时，放在 `.env.local` 里的密钥完全不生效，
  `pnpm start` 会直接以「缺少 DEEPSEEK_API_KEY」退出——用户很容易误以为配置文件已生效。
- 用 `-if-exists` 而不是 `--env-file`：文件缺失时静默跳过而非报错，
  新克隆的仓库无需先建文件就能跑起来。
- 分离两个文件符合「模板入库、真实值不入库」的惯例：
  `.env` 只含占位符，可安全提交；`.env.local` 存真实密钥，已在 `.gitignore` 中。

**代价**：脚本变长；`test` 也会加载 env 文件。后者对本项目无实际影响——所有测试
都用注入的替身，不读 `process.env`，因此不依赖这两个文件。保留它是为了
`start` 与 `test` 行为一致。

## D13. 错误输出走 stderr，与模型回答分流

**决策**：`ReplOptions` 增加必填的 `errorOutput`，REPL 捕获到的错误写 stderr；
`output`（stdout）**只承载模型回答**。`index.ts` 传入 `process.stderr`。

**理由**

- spec §8 明确要求「打印错误到 stderr」。分流后 `pnpm start > answers.txt`
  得到的文件里只有回答；管道场景下也能按流分别过滤（例如 `2>/dev/null` 屏蔽诊断）。
- **把两条流都做成注入参数**，分流本身才成为可断言的行为。只注入一条流时，
  「写错流」这类偏差测不出来 —— 初版 12 个用例全绿却掩盖了它。

**代价**：`ReplOptions` 多一个必填字段，调用点与测试都要同步传参
（生产调用点只有一个：`src/index.ts`）。

## D15. 一轮对话的终端形状：`You: ` 与 `AI: ` 前缀

**决策**：输出形状严格对齐需求 —— spec §2 与 `README.md` 画的是同一份：

```text
You: 什么是 React Server Components？
AI: ...
```

三条规则，缺一条形状就不对：

1. `AI: ` 前缀由渲染器在**第一段正文之前**写出，整轮只写一次；且**只在成功路径**上写
   —— 失败时 stdout 不会留下一个空的 `AI: `
2. `You: ` 提示符在**每次读取之前**写，不是只在循环开始前写一次
3. 提示符**不补换行** —— 它必须和用户输入同行（终端负责回显输入）

**为什么值得记一条**：这三条需求从一开始就写在文档里，却在**实施计划从 spec 转写时被丢掉**
（`AI: ` 在计划里出现 0 次），实现忠实执行了计划，缺陷藏了整轮 M1。**转写会丢东西** ——
写计划时必须逐节核对 spec；**断言要能证伪** —— `some()` + `includes()` 这类存在性断言
对计数与缺失都不敏感，输出形状必须逐字节比对。

**代价**

`repl.ts` 的循环从 `for await` 改成手写异步迭代器 —— 需要在「读取之前」这个时机写提示符，
而 `for await` 把读取藏在语法里拿不到。**串行语义不变**（上一轮 await 完才拉下一行），
与 D9 的选择一致。

**已知边界（有意保留）**：提示符写在读取之前，而 EOF 只有在读的时候才知道，所以
**最后一次提示符必然已经写出去**（`pnpm start < q.txt` 的输出以 `You: ` 结尾）。
文档没有规定退出时的行为，本次选择接受。若不想要，可给 `ReplOptions` 加一个 `showPrompt`
开关、由 `input.isTTY` 决定 —— 那会让输出变成模式相关的，本次不做。

## D16. `chatStream()` 与 `chat()` 并存，各自独立实现

**决策**：`LLMClient` 增加 `chatStream()`，`chat()` 保留为独立的非流式实现。

**理由**

- 这是学习项目。「非流式」与「流式」两条 wire 路径对照着看，正是阶段 0 要学的东西。
- 把 `chat()` 改成在 `chatStream()` 之上收集事件虽然只有一条路径，但会作废
  `deepseek.test.ts` 原有的 6 个非流式用例（它们喂的是 JSON 响应，不是 SSE）。

**代价**：`deepseek.ts` 里有两个请求构造点（各 2–3 个键，差异只有一个 `stream: true`）。
**特意不抽 `buildBody()`** —— 为这点差异抽 helper 会让「这次到底发了什么」变得不直观。

## D17. per-call `options` 携带模型，「当前模型」存在 `Session`

**决策**：`chat(messages, options?)` / `chatStream(messages, options?)`，
`options.model`；`Session` 增加 `model` getter/setter。

**理由**：`/model` 需要在会话中途切换模型，而原实现把 `config.model` 闭包捕获在
`createDeepSeekClient()` 里，模型在构造时就烧死了。

**为什么参数位迟早要有**：M4 的 `--no-thinking` 同样是 per-call 参数 ——
thinking 开关不是 client 的身份，是这一轮的属性。

**放弃**：repl 持 factory 切换时重建 client（要改 `runRepl` 签名，并作废 `repl.test.ts` 原有的 4 个用例）；
client 加可变 `setModel()`（接口有状态，多会话共享会互相污染）。

## D18. `StreamEvent` 只吐三种，`usage` 推迟到 M4

**决策**：M2 只产出 `text-delta` / `reasoning-delta` / `done`。

**理由**：`done` 必须现在有 —— `finish_reason === 'length'` 表示回答被截断，要告诉用户。
`usage` 现在解析了没有消费者，还要连带定义 `TokenUsage` 及其测试。

**代价**：M4 要在 `StreamEvent` 联合里加第 4 个成员。可接受。

## D19. SSE 解析是纯函数 + 显式残余缓冲

**决策**：`parseSse(chunk, buffer?) → { events, rest }`，无状态。

**理由**：分帧是 M2 最容易错的地方（一条事件可能被 TCP 切成两次 `read()`，
一次 `read()` 可能含多条事件）。纯函数才能用「喂字符串、断言字符串」测透，
而不必构造假的可读流。

**放弃**：有状态类（跨分片测试更绕，且引入可变状态）；
async generator 直接吃字节流（把分帧与读流揉在一起，正好把最难测的部分藏进 IO）。

**关键实现细节**：必须**先 `buffer + chunk` 拼接、后**把 `\r\n` 规范化成 `\n`。
反过来做的话，`buffer` 尾部一个落单的 `\r` 无法判断是否与下一块的 `\n` 成对。

## D20. `TextDecoder({ stream: true })` 在调用方解码，分帧在字符串层

**决策**：`deepseek.ts` 用 `new TextDecoder()` 配合 `decode(chunk, { stream: true })`
逐块解码，`sse.ts` 只处理字符串。

**理由**：SSE 按字节到达，一个中文 3 字节，很可能被 TCP 切在字符中间。
把跨块多字节序列的处理交给 `TextDecoder`，分帧逻辑就不必关心字节。

## D21. 一个 30s 的流空闲超时，不加开关

**决策**：`deepseek.ts` 内部一个每收到 chunk 就重置的计时器，常量 30s，
超时只 reject 并抛普通 `Error`，连接由流收尾的 `reader.cancel()` 收掉
（**没有** `AbortController`）。

**理由**：非流式卡住是「整个请求没响应」，用户明确知道在等；流式已经打印了
半句话然后停住，**用户无法区分「模型在想」和「连接死了」**。

**限定**：计时器是在拿到 `response.body` **之后**才建立的（`readWithIdleTimeout`），
所以它覆盖的只是「**响应头之后的**首字节」与 chunk 之间的空闲。`await fetch(...)` 之上
没有本项目的时限 —— 服务端接受连接却不回响应头时，要等 undici 默认的
`headersTimeout`（约 300s）。真正的首字节超时与 `--timeout` 开关归 M6。

**为什么不用单一总时长**：长回答会被误杀。

## D22. 思考过程走 stderr 一行指示

**决策**：首个 `reasoning-delta` 到达时往 stderr 写一行 `[思考中…]`，此后不再输出；
思考内容本身不打印。

**理由**

- 思考可能持续十几秒。这期间若一片死寂，流式解决的「等待没反馈」只解决了一半。
- 思考通常比答案长得多，打印出来会淹没答案（展开全文是 M4 的 `--show-reasoning`）。
- 走 stderr 而不是 stdout：stdout 只承载模型回答（D13）。

**副产品（好的）**：**不需要 TTY 检测**。两条流天然分流，管道与重定向都不会被污染。

## D23. spec §11「坏 JSON 累计计数 + 流结束警告」在 M2a 未落地

**事实**：spec m2 §11 要求「坏 JSON 跳过 + **累计计数、流结束时 stderr 警告一次**」，
M2a 只做了「跳过」（`deepseek.ts` 的 `catch { continue; }`）。**这是有意不做，不是失误** ——
spec 自己在别处把路堵死了：D-M2-3 把 `StreamEvent` 冻结为 3 个成员，没有事件能承载
「跳过了几条」；`llm/` 又不许写 stderr。且 §12 的测试清单只写了「被跳过」，与 §11 矛盾。

**落点**：**M6（错误分类）** —— 那一增量重做错误与警告的统一去向，顺手补上。

**教训**：spec 内部自相矛盾时，实施者按哪一节走都能让测试全绿，被放弃的那一行因此
最容易无声消失。**凡是明确不做的需求行，都要在 DECISIONS 里有编号可查**，而不是只在
计划里被默默改写。（D27 依此而立。）

## D24. 命令逻辑在 `core/`，打印在 `cli/`

**决策**：`core/commands.ts` 只做「解析 + 改 Session + 返回结构化结果」，
`cli/render.ts` 负责把结果变成文字。

**理由**：`core` 不许写 stdout（分层单向 `cli → core → llm`）。
拆开后命令的全部行为都能在无 IO 的情况下断言 —— 14 个 `commands.test.ts`
用例没有一个需要捕获输出。

**代价**：多一层 `CommandResult` 联合类型与一个渲染分支。换来的是命令逻辑完全可测。

---

## D25. 命令永不进入对话上下文

**决策**：命令在 `session.append('user', …)` **之前**处理。

**理由**：这不是优化，是必须的。

- `/clear` 若先进历史再清空，那条 `/clear` 就留在了刚被它清空的历史里
- `/history` 若进历史，下一轮模型会看到「用户查了历史」，污染推理
- `/model` 若进历史，模型会以为用户在跟它讨论模型名

**代价**：`repl.ts` 的循环里多两个 `continue` 分支。

## D26. 命令结果走 stdout，未知命令走 stderr（spec D-M2-10）

**决策**：把 D13 的规则细化为两条线 ——

| 流 | 内容 |
| --- | --- |
| stdout | 用户**主动要看的**：模型回答 + 命令结果 + `You: ` 提示符 |
| stderr | 用户**没主动要的**：错误、`[思考中…]`、截断警告、未知命令提示 |

注：`You: ` 提示符也算 stdout —— `repl.ts` 直接写 `options.prompt`，
所以重定向得到的文件里每一轮都有它。

**理由**：D13 原来的表述是「stdout 只承载模型回答」。但 `/history` 是用户显式索要的
输出，`pnpm start > answers.txt` 里看不到它反而反直觉 —— 用户要的东西应该出现在
他重定向的文件里。

**代价**：规则从「一条线」变成「要看用户是否主动索要」，判断成本略高。
但未知命令这类错误仍走 stderr，边界是清楚的。

## D27. `/history` 的多行消息按原样打印，续行会错位 —— 有意不修

**现状**：`renderCommandResult` 每条消息只写一行 ``${index + 1}. [${role}] ${truncate(content)}``。
内容含 `\n` 时（模型回答多段、用户粘贴多行）续行没有前缀，编号列表随之错位：

```text
1. [user] 第一问
2. [assistant] 第一段
第二段
3. [user] 第三问
```

**这是有意不处理，不是遗漏**：spec §10 只规定了 `N. [role] ` 的形状与 200 字符截断，
**对多行内容一个字都没写**；`test/render.test.ts` 也只用单行内容覆盖（没有一条用例
钉住多行行为）。

**两个候选修法都要付代价，所以不在这轮挑一个**

- **换行折叠成空格**：编号永远对得齐；代价是把「回答里有列表 / 代码块」这类结构压平，
  而用户最想复读的往往正是这种带结构的长回答
- **续行加缩进对齐**：保留内容结构；代价是新增一条 spec 没规定的格式规则 ——
  等于替用户发明格式

**为什么记成编号决策**：依 D23 的教训而立。`/history` 的用途恰恰是**长会话**，
会话越长「内容里带换行」越可能出现，这条边界藏不住，先记下来待有真实反馈时再定。

**落点**：暂不排期；M4 之后若给 `/history` 加过滤 / 分页，顺手把格式一并定下来。

## D28. 会话日志是**事件流**（meta / message / model / clear），不是纯消息

**决策**：`.sessions/<id>.jsonl` 一行一条 JSON，共四种记录；回放就是按顺序折叠这四类记录。

```jsonc
{"type":"meta","id":"20260924-143022-a3f1","createdAt":"…","model":"deepseek-flash"}
{"type":"message","role":"user","content":"什么是闭包"}
{"type":"model","model":"deepseek-v4-pro"}
{"type":"clear"}
```

**放弃：只存 `{"role","content"}`。** 格式最简、回放就是直接拼数组 —— 但 `/clear` 之后
旧消息仍留在文件里，`--resume` 会把用户**明确清掉**的内容又恢复回来；`/model` 的切换
同样无处安放。这是语义错误，不是取舍。

**代价**：解析侧要认四种记录，回放要按顺序折叠。多出来的这条规则有对应收益：
`clear` 只清消息、不清模型（与 `Session.clear()` 严格对齐），所以「清空对话但保留
当前模型」这件事在回放后依然成立。

## D29. `Session` 广播变更、cli 落盘；不采用「repl 手动写」

**决策**：`Session` 在三个变更点（`append` / `clear` / `set model`）改完状态后调用注入的
可选回调 `onChange(change)`；`cli/repl.ts` 收到就追加一行。**先改内存、再广播**。

**理由**：四个变更点里有两个藏在 `executeCommand` **内部**（`/clear` 调 `session.clear()`、
`/model <name>` 写 `session.model`），repl 的循环里看不见它们，只能靠 `result.kind`
反推。靠「记得写」的写法漏一处，就是磁盘悄悄落后于内存，而且这类不一致很难测出来。
广播让它从结构上不可能漏。

**放弃：包一层 `JournaledSession` 组合类。** 理论上更解耦，但 `Session` 带 `private`
字段，TS 的结构化兼容会失效，`executeCommand(…, session: Session)` 的参数类型就得改成
接口 —— 改动面反而比广播大。

**代价**：`Session` 不再是「无副作用」的纯类，类注释因此重写（新注释以「默认仍是纯的，
副作用由注入的回调承担」立论）。回调可选，所以不传时行为与 M1 完全一致。

**守住的边界**：**只读操作永不广播** —— `toMessages()` / `history()` / `get model`
（`/model` 的查询分支）都不写状态、也就不写日志。`commands.test.ts` 现有的
「查询分支一次都不写 `session.model`」探针用例钉的正是这条。

## D30. 落盘位置：项目内 `.sessions/`，`AI_CHAT_HOME` 可覆盖

**放弃：`~/.ai-chat/sessions/`** —— 跨项目共用、不污染仓库，但想看内容得跳出仓库，
对学习项目不直观。
**放弃：`$XDG_DATA_HOME/ai-chat/`** —— 最正统，但 macOS 上落到 `~/.local/share/...`，
又长又不直观，还要多一层「未设时回落」的逻辑。

**代价（已知，写进了 README）**：目录跟着 **cwd** 走 —— 换个目录启动就是另一份会话。
这不是 bug 而是选定行为，但不知道这一点的人会当成 bug。

`.sessions/` 已加进 `demos/01-llm/.gitignore`（会话内容不该进仓库）。

## D31. 启动即建文件写 meta；用 `wx` 独占创建

**理由有二**：① 启动时要把本次 id 打到 stderr 供 `--resume` 用，若文件还不存在，用户
拿着这个 id 去 resume 会得到「会话不存在」，自相矛盾；② 「目录不可写」这类错误应当在
启动时就暴露，而不是聊到一半才发现存不了。

**放弃：延迟到第一条记录才建文件。** 好处是不留空文件，但上面两个问题都会回来。

**代价**：启动后立刻 Ctrl+D 会留下一个只有 meta 行的文件。可接受（一行，`/sessions`
里显示 0 条）。

**打开方式必须是 `wx`，不能用 `w`。** `w` 会**静默截断**已存在的文件 —— 万一 id 撞名
（随机后缀只有 4 位十六进制），用户的旧会话会被无声抹掉。`wx` 在文件已存在时抛错，
由启动流程报出来（属「致命」档：stderr + 退出码 1）。

## D32. 会话 id 白名单校验 + 路径包含检查，两道防线

**决策**：id 格式固定为 `YYYYMMDD-HHMMSS-xxxx`（`xxxx` 为 4 位小写十六进制），
`isValidSessionId` 用 `/^\d{8}-\d{6}-[0-9a-f]{4}$/` 校验；`cli/store.ts` 拼出绝对路径后，
再用 `full.startsWith(root + sep)` 确认它确实落在会话目录内。

**为什么必须校验**：id 来自命令行、会被拼进文件路径，`--resume ../../etc/passwd`
就是一次路径穿越。两道都要有 —— 正则保证「现在的 id 长什么样」，包含检查保证
「即使将来正则被放宽，也走不出会话目录」。

**注意 `sep` 不能省**：只比 `startsWith(root)` 的话，`/tmp/sessions-evil` 这种同前缀的
兄弟目录也会被放行。

**代价**：id 的形状被定死，将来想换成人可读的名字（比如带主题词）就得同时改校验与
所有旧文件。

## D33. 坏行跳过并计数，不因一行坏掉丢掉整个会话

**决策**：JSON 解析失败、或形状不认识的行 → 静默跳过并计数，`--resume` 时在 stderr
警告一次「已跳过 N 行」。

**放弃：遇到坏行直接报错退出。** 一行损坏就让整场会话不可恢复，代价和收益不成比例。
进程被 kill 时写下的**半行**走同一条路径 —— 这正是不做自动化测试时最容易漏掉的情形。

**注意「空行不算坏行」**：文件末尾那个换行 `split('\n')` 之后就是一个空串，把它计成
坏行会让每个正常文件都报「跳过 1 行」。

## D34. 写盘失败分两档：建文件失败致命，`append` 失败警告一次后继续

| 时机 | 处理 | 理由 |
| --- | --- | --- |
| 建文件 / 写 meta 失败 | **致命**：stderr + 退出码 1 | 存不了的会话没必要开始，早点死 |
| 后续 `append` 失败 | stderr 警告**一次**，对话继续 | 磁盘满不该打断正在进行的对话 |

「只警告一次」是刻意的：每轮都刷同一句会把屏幕占满，反而看不见别的。
**绝不静默**同样是刻意的 —— 写盘失败却一声不吭，用户会以为存下来了，比直接报错更糟。

**放弃：一律致命**（对话被打断）、**一律静默**（用户被误导）。

## D35. `/sessions` 给当前会话打 `*`；会话 id 不进 `Session`

**决策**：`executeCommand` 通过依赖注入拿到 `currentSessionId`，渲染时行首打 `*`，
其余行补一个空格对齐。展示用的时间**从 id 切片**得到，不读 meta 里的 `createdAt`。

**放弃：把 id 放进 `Session`。** 归档蓝图确实把「会话 id」列为 `Session` 的职责，
但 `Session` 自己一次都用不到它 —— 只有渲染 `/sessions` 需要。为此加一个只读字段，
不如从 deps 传。

**理由（时间为什么从 id 切）**：id 里的时间**本来就是本地时间**（`makeSessionId` 逐段
取本地分量、不用 `toISOString()`），切片零换算、在哪台机器上都一样。走 `createdAt`
则要 `new Date(iso)` 再取本机时区，同一份文件换个 TZ 就显示成另一个时间。

## D36. 命令需要外部数据时走依赖注入（`CommandDeps`），core 不碰 IO

**决策**：

```ts
executeCommand(name, argument, session, deps)   // deps: { store, currentSessionId }
```

`/sessions` 要的会话列表由注入的 `store` 提供。这与 `LLMClient`（接口在
`llm/client.ts`、实现在 `llm/deepseek.ts`、测试塞假的）是同一个套路：
**接口在里层、实现在外层、调用方只认接口**。

**代价**：`commands.test.ts` 的每个调用点都要补一个 `deps` 参数（8 处）；
`runRepl` 的 options 也多出 `sessionId` / `history` / `store`（15 处）。
这些属于签名变更的必要代价，**断言一句没改**。

## D38. 还清 M3 的测试欠账：补测的范围与两条已确认缺陷

**背景**：D37 记下的欠账本次还清。补测清单来自 spec §12，行为契约来自 spec §7–§11。
用例数 **91 → 167**（新增 76 条）。

**新增测试文件**

| 文件 | 覆盖 |
| --- | --- |
| `test/journal.test.ts` | 记录的两向格式契约（手写 JSON → 解析 / 对象 → JSON.parse）、坏行与未知 type 跳过、`replay` 的四条规则、id 生成与白名单 |
| `test/store.test.ts` | **真临时目录、不 mock `node:fs`**：meta 独占创建、append 追加、load 的坏行计数与 ENOENT/EISDIR 之分、list 倒序与条数、路径穿越被拒 |
| `test/args.test.ts` | `--resume` 的六种非法输入各自抛错并附用法行 |

**扩充的既有文件**：`session`（变更广播）、`commands`（`/sessions`）、`repl`（落盘接线与降级）、
`render`（`/sessions` 列表渲染）、`index`（启动分支的子进程用例）。既有 91 条的断言一句没改。

**用变异检查代替「看着绿」**：测试是在代码之后写的，一写就绿本身不证明任何事。
逐条注入 20 个人为缺陷，确认对应用例真的变红，再还原（`git diff src/` 为空即证明未改生产代码）。
20/20 全部被抓住。—— 这是本次唯一的「测试确实有效」的证据来源。

**两条已确认的生产缺陷（本次只报告、未修改代码）**

1. **`store.append` 会静默创建缺失的会话文件**，与 `core/journal.ts` 里 `SessionStore.append`
   的注释契约「文件不存在时抛错」矛盾。成因：`appendFileSync` 的默认 flag `'a'` 在文件不存在时
   会创建它。影响：会话文件在对话中途被删/移走时，会凭空造出一个**没有 meta 行**的日志，
   于是 `replay` 的 model 为 null（丢掉用户切过的模型），`list()` 也会把它当正常会话列出。
   已用一条表征用例钉住当前行为（`【已知缺陷】` 前缀），修好后那条用例会变红、应当改成
   `assert.throws`。**修法不要**简单把 flag 改成 `'r+'` —— `appendFileSync` 用 `'r+'` 时写入起点是 0，会覆盖文件开头。
2. **`store.pathOf` 的第二道防线对 `dir === '/'` 误报**：`root + sep` 成了 `'//'`，而
   `resolve('/', name)` 是 `'/name'`，`startsWith('//')` 为 false → 合法 id 被判「会话路径越界」。
   这条同时说明该防线当下的处境：正则先行已排除 `/` 与 `.`，任何穿越类输入都在
   `isValidSessionId` 就抛了，所以这道检查在正则不放宽时**唯一可达的路径就是这个误报**。
   修法：拼接前缀写成 `root === sep ? sep : root + sep`，或改用 `path.relative()`。

**一条已知边界（不是缺陷，未改）**：`Session` 构造函数用 `[...options.history]` 浅拷贝 ——
数组是新的，但 `Message` 元素与调用方共享，调用方改元素字段会穿透进会话状态。
与 `history()` 刻意做的元素级深拷贝不对称。**当前不可达**：唯一调用方 `src/index.ts`
传的是 `replay()` 现造的新对象且随后丢弃。将来若有调用方复用传入的数组或元素，这里必须升级成元素级拷贝。

**时区用例为什么要锚定 `TZ`**：`makeSessionId` 的「本地时间而非 UTC」这条契约，
在 `TZ=UTC` 的机器上两种实现结果逐字符相同 —— 断言会**静默退化成空转**（正是 D37 抱怨的那种
「看着绿但什么都没说明」）。因此 `test/journal.test.ts` 在模块作用域执行
`process.env.TZ = 'Asia/Shanghai'`（`node --test` 每文件一个子进程，作用域只到本文件），
并加了一条**前置条件用例**断言该赋值确实生效 —— 万一某个平台忽略运行时 TZ 变更，
那条会大声失败并说明原因，而不是让主断言悄悄空转。
