# 设计决策记录

> 回答：为什么是这样设计的，放弃了什么？

每条写三件事：**理由 / 放弃了什么 / 代价**。编号沿用设计文档 §18 的 D1–D21，不重新编号 ——
这样它与 `docs/superpowers/specs/2026-09-25-ai-chat-agent-web-design.md` 一一对得上。

---

## D1 阶段之间复制，而不是共享依赖

**理由**：阶段之间是复制关系。整份复制阶段一的 M3 底座会把已经学过的 readline、
stdout/stderr 分流、JSONL 落盘一并拖进来，而那些与 Tool Calling 无关。
复制范围限定为 4 个文件：`core/types.ts`、`core/session.ts`、`llm/client.ts`、`llm/deepseek.ts`，
其余全部新写。

**放弃了**：一次修复惠及两个阶段的可能性。

**代价**：同一个 bug 可能要在两个阶段各修一次。由此推出一条硬规则：**旧阶段只读不改**；
若某次改动需要同时改两个阶段，说明该抽共享包了 —— 先把那个判断写进本文件，再动手。

---

## D2 不做 CLI 入口

**理由**：CLI 买不到任何与 Tool Calling / Agent Loop 相关的东西，它买的是阶段一已经买过的经验。
**整个不做**，不是「以后补」。

**放弃了**：终端调试器（`curl` 可替代）与「一套 core 换两种前端」的演示。

**代价**：失去那条演示。但 `test/agent.test.ts` 已离线证明 core 不依赖任何入口。

---

## D3 不做会话持久化

**理由**：与 D2 同源。直接收益是一整串工作**根本不需要做**：会话日志格式升级
（`SessionChange` 承载 tool 消息、`parseRecord` 白名单、老 `.jsonl` 字节级兼容），
连带四条风险一起消失（`parseRecord` 写 `undefined` 键、`/history` 遇到 `content: null` 崩溃、
`SYSTEM_PROMPT` 把 `node:readline` 拖进服务端、老文件兼容）。

**放弃了**：落盘、恢复、以及阶段一辛苦建立的日志格式。

**代价**：刷新页面靠服务端内存，**服务端一重启，所有会话就没了**。前端对此的处置是
静默清掉本地 id 并给一条可关闭的提示，而不是白屏（见 `ARCHITECTURE.md` 与 `docs/troubleshooting.md`）。

---

## D4 agent 层只产出事实，展示投影全在外层

**理由**：`runAgentTurn` 只返回 `{final, added, stopReason}`；`TranscriptItem` 放在
`presentation/` 而不是 `core/`。core 里若保留一个带 `index` 与 `ms` 的步骤结构，
`ms` 会变成「唯一非确定字段，测试不得断言」—— agent 层的输出形状就被 UI 塑形了。

**放弃了**：界面区分「参数非法」与「工具执行失败」的能力。

**代价**：前端只能看到一个 `ok: boolean`。这是有意接受的 —— 两者的错误文本本身就写着原因
（`参数不是合法 JSON：{city: Beijing` 与 `无法计算「1/0」：除数不能为 0`），用户信息没有损失。

---

## D5 不做 SSE / `chatStream` / `sse.ts` / `StreamEvent`

**理由**：无入口的代码会变成下个里程碑的既成事实。下个里程碑做「流式 + 工具」时，
分片 `tool_calls` 的拼接本来就要另写一套，留着只是重写前的负担。

**放弃了**：打字机效果；以及把阶段一调好的空闲超时逻辑直接拿来用。

**代价**：`LLMClient` 本次只有一个方法 `chat()`。阶段一留下的
`chatStream` / 空闲超时 / `sse.ts` 在 L3 被整体删除。

---

## D6 `Session` 保持纯类

**理由**：只留 `append` / `appendMessage` / `appendAll` / `toMessages` / `history`。
阶段一的 `onChange` / `clear()` / `set model` / 构造时的 `history` 参数不复制过来。

**放弃了**：变更广播、清空、切模型、从历史恢复。

**代价**：无实际代价 —— 它们各自的唯一消费者是落盘、`/clear`、`/model`、`--resume`，
本项目都不做（见 D2、D3）。去掉之后它退回成一个无副作用的纯类，这正是它最好测试的形态。

---

## D7 循环条件看 `tool_calls`，不看 `finish_reason`

**理由**：部分 OpenAI 兼容实现会在 `finish_reason: 'stop'` 的同时返回 `tool_calls`。

**放弃了**：一个「按协议语义判断」的直觉写法。

**代价**：若不这样做，症状是**漏调工具 + 把 `content: null` 当成最终答案回给用户**
（前端显示一个空气泡），**而且不报任何错** —— 排查成本极高。测试落点：
`test/agent.test.ts` 的 `finish_reason 是 stop 但带 tool_calls：仍要执行工具`。

---

## D8 工具失败回喂模型，而不是崩溃

**理由**：参数非法、工具抛异常、工具名不存在 —— 三种都变成 `tool` 消息让模型自己纠正。
错误文本是模型唯一的纠错线索，所以必须带上原文（表达式原文、参数名）。

**放弃了**：让异常直穿到 HTTP 层由框架统一处理。

**代价**：「兜底」只允许发生在一处（`core/agent.ts`），所以 `tools/registry.ts` 刻意
**不** try/catch —— 否则行为会随调用方而变。

---

## D9 `maxSteps` 防死循环（默认 6）

**理由**：循环必须有界。跑满时追加的最后一条**必须是带 `content` 的 assistant**。

**放弃了**：让模型自己决定什么时候停。

**代价**：极复杂的问题会被截断在 6 步。留一条只有 `tool_calls` 的消息在末尾是不可行的 ——
那样的历史对上游 API 非法。

---

## D10 weather 用确定性 mock

**理由**：本阶段的学习目标是 tool calling 这条链路本身（模型怎么开调用单、程序怎么执行、
结果怎么回喂），不是「怎么调第三方天气 API」。用一张内置小表把网络这个变量消掉，
失败原因才能收敛到链路自己身上。

**放弃了**：一个更「真实」的演示。

**代价**：模型可能把编出来的天气当事实转述给用户 —— 所以**未命中**时返回的兜底值里
必须带一条 `note` 说明是模拟数据。（命中路径不带 `note`，这是有意的：spec 的手动冒烟
正是期望它被当作事实转述。）

---

## D11 calculator 用白名单正则 + 受限算术求值器

**理由**：模型给的表达式是外部输入，直接喂给 `eval` / `new Function` 等于把一个任意代码执行
的口子开在最不该开的地方。这道防线本身也是教学内容：**工具的参数是不可信输入**，
哪怕它看起来只是一个算式。

**放弃了**：几行就能写完的 `eval`；以及由此能支持的任意数学函数。

**代价**：只支持 `+ - * / ( )` 与数字，要手写词法分析与递归下降求值。
白名单是**第一道**防线，真正保证安全的是求值器本身 —— 它只会做加减乘除，
即使白名单被绕过也执行不了别的东西。

---

## D12 服务端引入 `express`

**理由**：本仓库**第一个运行时依赖**，破掉「零运行时依赖」这条跨阶段约束。
选 express 5 的决定性理由是：**它的 async handler 抛出的 rejected promise 会自动转给
错误中间件**，4 需要手写包装。

**放弃了**：零运行时依赖；以及用 `node:http` 手写路由的练习。

**代价**：`http/` 层从此可以 import express（其它四层仍然禁止），
且这条依赖必须在根 `AGENTS.md` 的跨阶段约束里登记。

---

## D13 前端用 React + Vite，放在 `apps/web`

**理由**：本仓库**第一个前端构建步骤**，破掉「不引入构建步骤」。
前端是那条约束的**唯一例外**：它有自己的 `package.json`、`tsconfig.json` 与 Vite 配置，
不进服务端的 `pnpm test` / `tsc --noEmit` 口径。

**放弃了**：原生 HTML/JS（能守住零构建）；Vue CDN（不引入构建，但引入外部 CDN 依赖）。

**代价**：仓库里从此有两套工具链。

---

## D14 前端不引测试框架，但 reducer 拆成纯模块

**理由**：`chatReducer.ts` 是纯函数、不 import React，这样将来补测试时不必重构。

**放弃了**：本次的前端测试覆盖。

**代价**：这是一笔**已知欠账**。`EVALUATION.md` 里必须写明，半年后不能误以为前端有测试覆盖。

---

## D15 前端类型手写一份，不跨包共享

**理由**：本次只做「两个 app」，还没有值得抽 `packages/` 的第三份共享代码。
跨包 import 服务端类型会把服务端的 `@types/node` 拖进前端 tsconfig，
而那份 tsconfig 刻意设了 `types: []`。而且线上契约本来就不是服务端的内部 `Message` 联合，
它是 `TranscriptItem`，是另一个东西。

**放弃了**：编译期就发现前后端契约漂移的能力。

**代价**：真正的守卫变成运行期的一条测试 —— `apps/server/test/http-app.test.ts`
里逐字断言响应 JSON 的键与形状。改 `apps/web/src/types.ts` 而没改那边，服务端测试**不会红**。

---

## D16 会话 Map 用 FIFO 上限 100

**理由**：淘汰代价为零 —— 被淘汰的会话本来就没人再用。

**放弃了**：LRU（更贴合真实使用模式）。

**代价**：长期活跃的会话也会被更晚创建的会话挤掉。

---

## D17 只监听 `127.0.0.1`，不做鉴权与 CORS 白名单

**理由**：这是个本机开发工具，不是可暴露的服务。

**放弃了**：任何形式的部署形态。

**代价**：Vite dev server 与 express 不同源，靠 **proxy** 而不是 CORS 打通 ——
所以前端代码里一律用相对路径 `/api/...`，写成绝对地址会绕过 proxy 并触发 CORS 报错
（正解不是加 `cors` 中间件，见 `docs/troubleshooting.md`）。

---

## D18 展示投影只定义一次

**理由**：实时路径（本轮新增）与历史路径（读回整段会话）共用同一个 `foldTranscript`。

**放弃了**：让两个接口各自返回最贴合自己的形状。

**代价**：`GET` 的响应比「只给历史」多了一层折叠。换来的是前端只需要一套渲染逻辑 ——
否则要写两套，而两套迟早不一致。

---

## D19 仍非流式

**理由**：见 D5。这一条与 D5 是同一件事的两个面：D5 说「删掉流式代码」，
D19 说「新增的也不做流式」。

**放弃了**：首字节延迟上的体验。

**代价**：长回答要等完整一轮才显示。

---

## D20 不自动重试

**理由**：对齐阶段一的 D5。这一层把非 2xx 统一抛出，交给调用方决定怎么显示。

**放弃了**：对 429 / 5xx 的自动恢复。

**代价**：上游抖动会直接变成用户看到的一次失败。`http/errors.ts` 把它映射成
502 / 504（**绝不透出上游状态码**）。

---

## D21 阶段目录用 pnpm workspace，而不是「根即服务端」

**理由**：后者会让 `demos/02-agent/package.json` 既当阶段根又当服务端，`src/` 与 `web/`
的地位看不出区别。`apps/` 下两个平级应用把边界写在名字里，且阶段根仍能一条命令跑全部。

**放弃了**：更扁平的目录。

**代价**：多一层 `apps/`，且 `pnpm -F <app>` 这样的命令变多。

**这在仓库里是第一次**：跨阶段约束「各阶段是独立项目」指的是**阶段之间**，
阶段内部的组织形式不在此列。
