ai-chat · 多轮对话是怎么工作的

模型不记得你

看代码之前，先接受一个反直觉的事实：DeepSeek 的接口不保存任何东西。 你问第二句话时，它并不知道你第一句问过什么。

所谓「多轮对话」，是你的程序每次把之前说过的所有话，连同新问题一起重发一遍。

所以「上下文管理」不是什么黑魔法 —— 它就是维护一个数组。 整个 src/ 里所有的代码，都在为这一个数组服务。

第一步

API 是无状态的

你的程序问两次，就是两次互不相干的 HTTP 请求。 服务端每次都「第一次见到你」，收到什么就答什么，答完就忘。

第二步

一轮对话，代码做了什么

循环里只有 6 个动作。左边是发生的事，下面灰色的是对应代码。 注意第 4 步 —— 那一次 fetch 就是全部的「网络魔法」。

第四步

代码里三个容易卡住的地方

system 为什么不在数组里？

因为它不是「说过的话」，而是每次请求都要重新附上的固定指令。 所以它存在常量里，由 toMessages() 在组装时插到最前面。 这样改助手人设不用重建会话。

请求失败时会怎样？

不往数组里加 assistant。 否则历史里会出现一条「伪造的回答」，下一轮模型会把它当成自己说过的话。 失败的 user 会留着 —— 用户确实说过那句。

reasoning_content 呢？

那是模型的思考过程。代码只用 content， reasoning_content 既不打印、也不进数组 —— 否则会白白占掉后续请求的 token。

关联知识

createInterface 并不触发请求

第 01 步用的是 createInterface，很容易以为「是它去调了模型」。 其实它不知道模型的存在 —— 它连 HTTP 都不认识。

它只做一件事：把 stdin 上的字节流，切成一行一行的字符串。 真正把「一行输入」变成「一次 HTTP 请求」的，是紧接着的那个 for await 循环。

它为什么要「先缓存」

终端来的字节是可能被切开的。你敲「你好⏎」时，底层可能先给 "你"，再给 "好\n"。 readline 负责把这种半行拼回去 —— 这正是它存在的理由。

为什么必须是 for await

rl 同时是两种东西：一个 EventEmitter（所以 rl.on('line') 能用），也是一个 AsyncIterable（所以 for await 能用）。两种写法都能拿到行，但 触发时机完全不同。

for await · 拉（pull）

循环体里的 await 会让 rl.next() 停下来 —— 上一轮彻底跑完，才会拉下一行。天然串行。

rl.on('line') · 推（push）

事件一到就触发回调，不等上一次跑完。 三行同时到达时，三个请求同时在途。

自己跑一遍

上面的图不是示意，是真实测量的。演示脚本就在项目里， 是个独立文件，不依赖任何依赖： examples/readline-pull-vs-push.mjs

$ node examples/readline-pull-vs-push.mjs

核心差别只有一行 —— 要不要 await： 

A：for await —— 每轮跑完才拉下一行
for await (const line of rl) {
  const q = line.trim();
  if (!q) continue;
  marks.push(await ask(q));   // ← await 让循环停住，串行的来源
}

B：rl.on('line') —— 行一到就触发，不等上一次
rl.on('line', (line) => {
  const q = line.trim();
  if (!q) return;
  pending.push(ask(q));       // ← 故意不 await，请求同时在途
});

实际输出（跑 3 次结果一致）：

A. for await —— 拉模型，串行
  发出顺序  一 → 二 → 三
  完成顺序  一 → 二 → 三        ← 与提问顺序一致
  总跨度    605ms

B. rl.on('line') —— 推模型，并发
  发出顺序  一 → 二 → 三
  完成顺序  三 → 二 → 一        ← 被打乱
  总跨度    301ms               ← 只等于最慢那个

串行为什么是必需的

顺序一乱，不只是回答的显示顺序错了。真正的问题在于： session.append('assistant', ...) 是在 await client.chat(...) 返回之后才执行的 —— 也就是按「回答到达的先后」写入数组。

并发时谁先返回谁先进数组，对话历史就变成了 「问一、问二、问三、答三、答二、答一」。模型下一轮看到这种自相矛盾的历史， 推理就崩了。多轮对话的正确性，完全建立在串行之上。

循环怎么结束

三种情况其实是一回事 —— 输入流结束：Ctrl-D、 管道读完、stdin 被关闭。此时 readline 发出 close， 迭代器的 next() 返回 { done: true }，循环退出， runRepl 的 Promise resolve，进程自然退出。 不需要手动 process.exit() —— 这也是为什么 printf 'x\n' | pnpm start 能自己跑完。

两个容易忽略的细节

为什么要把 output 传进去？

当 stdin 是真实终端时，readline 需要用它在屏幕上回显你敲的字、 处理退格和左右方向键。如果只做「读行」，其实可以不给。

提示符是谁打印的？

我们没用 readline 自带的 prompt 机制，而是自己 write 了一次。 所以它只在启动时出现一次 —— 想让每轮都提示， 在循环体末尾再写一次即可。
